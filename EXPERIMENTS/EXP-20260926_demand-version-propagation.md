# EXP-20260926_demand-version-propagation

- **hypothesis**：改一次 Demand 的版本，十分钟内"受影响 Task 被重新判断 → State 重生成 → 首页更新"三处自动成立；若不成立，说明"三套系统变成一个项目"只是叠了层皮。
- **baseline**：升版前 `generated/state/D-002.json` 为 `demand_version: 1`、`input_hash: 5e7980d3991d`、活动任务 8 项、`task_recheck_required: 0`；首页无待重判行。此前该链路从未被真实触发过，只有阶段 2 的一次哈希对比（那只能证明确定性，证明不了传播）。
- **candidate**：`runners/build_state.mjs` 读上一份 State 快照比对版本，变化即把该 Demand 下全部活动任务列入待重判，并同步渲染进首页与 `CURRENT_STATE.md`；另落一份追加式队列 `machine/recheck_queue.md`。
- **metric**：五项同时成立才算通过 —— ① `demand_version` 变 2；② `input_hash` 变；③ 活动任务全部进入重判清单（应等于 8）；④ 首页出现"待重判"行；⑤ 队列文件出现带真实任务号的条目。时限 10 分钟。谁测：本地执行模型，命令输出即证据。
- **observation_window**：单次构建内可测（实测 <1 秒），但**一次性标记的存续期**需要跨两次构建观察 —— 本实验正是靠第二次运行才暴露"标记会闪没"。
- **risk**：生成物可整目录删除重建，原生真源未被写（生成器只读取看板与 Demand）。回滚 = `git revert` 两个看板提交 + 删除 `generated/`。实测看板改动删除行数为 0，表格本体未动。
- **result**：五项全中。`input_hash` 由 `5e7980d3991d` → `4ab420a049007ce2`；`demand_version` = 2；重判 8 项，任务号真实（`workflow:T2/T5/T7/T9/T10/T11/T13/T14`）；首页第 18 行出现"待重判：Demand 版本 1 → 2，8 个活动任务需重新判断"；队列文件生成并含同样 8 条。耗时 <1 秒。
  过程中测出两个缺陷并当场修掉：① 队列模板把字符串当对象取字段，首版写出一排 `undefined`；② **重判标记是一次性的**，下一次构建就归零 —— 若没人恰好在中间看过首页，信号等于没发过。因此补了追加式队列，让"必须被处置"这件事留下不可消失的记录。
  处置结果：8 条逐条重判，全部仍服务 D-002、无一改绑；4 条需增补验收标准（T5 契约缺"送达回读"闸门、T7 skill 缺"凭证齐才判读到"、T11 跑通判据缺凭证项、T14 周报可加送审失败率），2 条建议增补探针判据（T10 应能发现今晚这两类读取侧失效）。增补未在本轮执行 —— 改契约与 skill 属换方案性质，按本目录规则须先建实验基线。
- **decision**：**adopt**。传播链成立，且实验顺带暴露并修掉了"信号只闪一下"的真漏洞。后续任何 Demand 升版都走这条链，重判队列未清空前不切默认入口。
